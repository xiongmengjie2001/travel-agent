# Code Review Skill

## 审查维度

### 1. 编码规范
- 遵循PEP8？
- 有type hints？
- 函数长度 ≤ 50行？
- 命名清晰？

### 2. 逻辑正确性
- 边界条件处理？
- 空值处理？
- 循环/递归终止条件？
- 异常处理完整？

### 3. 架构合规
- 模块职责单一？
- 无循环依赖？
- 接口与SDD一致？
- 无硬编码？

### 4. 安全性
- 无硬编码密钥？
- 用户输入有校验？
- SQL注入防护？
- 路径遍历防护？

### 5. 可维护性
- 有docstring？
- 有单元测试？
- 日志合理？
- 错误信息友好？

## 使用方法

对目标文件执行五维逐项检查，输出审查报告。

具体条目、判定标准与可执行的核对命令见 [checklist.md](./checklist.md)。**逐条过**，
不要只看被改动的行 —— 五维里有三维（架构、安全、可维护性）的问题通常不在 diff 里。

## 本仓库的补充规则

审查本仓库代码时，以下项目约定优先于通用规则（来源：根目录 `CLAUDE.md`）：

| 规则 | 含义 |
| --- | --- |
| 依赖方向 `api/ → src/` | `src/` 不得 import FastAPI 或任何 Web 框架；反向依赖一律 fail |
| 模块间只用 Pydantic 模型 | 裸 `dict` 传参禁止，**例外仅三处**（见下） |
| 禁止硬编码 API Key | 必须从环境变量读取 |
| 禁止 `print` | 只用标准库 `logging`，级别 INFO 及以上 |
| 函数 ≤ 50 行 | 超长是重构信号，不是风格偏好 |
| SDD 先行 | 新功能必须有对应 `docs/module-sdd/*.md`；代码写完后对照 SDD 验收 |
| 禁止删除或绕过测试 | 包括 `skip` / `xfail` 掉失败用例 |
| 禁止提交 `.env` | 只提交 `.env.example` |

### 误报豁免清单（不要报为违规）

以下四处裸 `dict` 是**经确认保留的例外**，命中即跳过，不要记为问题：

1. `ToolCenter.call(name, **params)` 的展开传参
2. `Bridge.parse_chat_request(payload: dict)` 的入参
3. `Bridge.to_api_response() -> dict` 的返回值
4. `api/routes.py` 中 `POST /api/chat` 以 `dict` 接收请求体（HTTP 入口边界，原样交给第 2 处）

同样豁免：`Mock` 数据（`src/tools.py` 顶部常量区，`docs/module-sdd/tools.md` §0 已登记，属阶段内计划偏差）；SDD 与代码签名不一致但**已在 SDD 中回写说明**的条目（如 `to_trip_card` 的 `trip_id` 参数、`save_trip` 的 `intent_raw`、`_call_deepseek` 的 `-> str | None`）。

## 输出格式

```markdown
## 审查范围
<文件列表 + 依据的 SDD / 提交>

## 问题清单

| # | 维度 | 位置 | 严重度 | 问题 | 建议 |
|---|------|------|--------|------|------|
| 1 | 安全性 | src/x.py:42 | 高 | API Key 硬编码 | 改读 os.getenv(...) |

## 五维结论
| 维度 | 结果 | 说明 |
|------|------|------|
| 编码规范 | pass / 2 项 | ... |

## 未覆盖
<哪些文件/维度没查，为什么>
```

严重度定义：

- **高** —— 安全漏洞、数据丢失、错误码/契约不符、测试被削弱
- **中** —— 逻辑边界缺失、异常未收敛、SDD 偏离未记录
- **低** —— 命名、注释、可读性

## 硬性要求

1. **每条问题必须给出 `file:line`**，无法定位的不写进清单。
2. **不得为了凑数报问题** —— 没有就写「未发现问题」，并说明查了什么。
3. **修复建议要具体到改法**，不要只说「建议优化」。
4. **不擅自修改代码** —— 审查只出报告，改动等用户确认。
